# Getting the three connection strings

This walks through obtaining `MONGODB_URI`, `AZURE_STORAGE_CONNECTION_STRING`,
and the Auth0 values, then putting them into the local `.env` files.

The `.env` files already exist — they were copied from each app's `.env.example`
and are gitignored. You are filling in blanks, not creating files.

| File | What goes in it |
|---|---|
| `apps/api/.env` | Everything secret. Never leaves the server. |
| `apps/portal/.env` | Auth0 **public** client identifiers only. Vite inlines these into the browser bundle. |
| `apps/portfolio/.env` | Just the API URL. Nothing to obtain. |

Do the three services in any order. Budget about 30 minutes for the first run.

---

## 1. MongoDB Atlas → `MONGODB_URI`

### 1.1 Create the account and cluster

1. Go to https://www.mongodb.com/cloud/atlas/register and sign up (Google sign-in
   is fine).
2. On the "Deploy your cluster" screen pick **M0 / Free**.
3. Provider: **Azure**, region whichever is nearest you — keeping the database
   near the API region matters later, since the API is going on Azure App
   Service. The free tier only offers a handful of regions per provider; if none
   are close on Azure, AWS is fine for development.
4. Name the cluster something like `wroom-dev`. Click **Create Deployment**.
5. Atlas immediately shows a "Connect to Cluster" modal offering to create a
   user. You can use it, but the steps below do the same thing from the sidebar
   and are easier to redo later. Close the modal.

Provisioning takes 3–7 minutes. You can do the next two steps while it builds.

### 1.2 Create a database user

1. Left sidebar → **Database Access** → **Add New Database User**.
2. Authentication Method: **Password**.
3. Username: `wroom_api`.
4. Password: click **Autogenerate Secure Password**, then **Copy** it somewhere
   safe *now* — Atlas will not show it again.
5. Database User Privileges: **Read and write to any database**.
6. **Add User**.

> **Password characters matter.** The password sits inside a URL, so any
> `@ : / ? # [ ] %` in it must be percent-encoded or the URI silently parses
> wrong. Autogenerated passwords are alphanumeric and safe. If you set your own
> and it contains a symbol, encode it: `@` → `%40`, `:` → `%3A`, `/` → `%2F`,
> `#` → `%23`, `%` → `%25`.

### 1.3 Allow your machine to connect

1. Sidebar → **Network Access** → **Add IP Address**.
2. For local development: **Add Current IP Address**. Comment: `Jaya laptop`.
3. **Confirm**.

If your home IP changes you will get a connection timeout on `npm run dev:api`
and have to add the new one. `0.0.0.0/0` (allow from anywhere) works and is what
you will eventually need for Azure App Service, but do not leave a dev cluster
open to the world casually — add the App Service outbound IPs when you deploy.

### 1.4 Copy the connection string

1. Sidebar → **Clusters** → **Connect** on `wroom-dev`.
2. Choose **Drivers**.
3. Driver: **Node.js**, Version: **6.7 or later**.
4. Copy the string shown. It looks like:

```
mongodb+srv://wroom_api:<db_password>@wroom-dev.ab12cde.mongodb.net/?retryWrites=true&w=majority&appName=wroom-dev
```

### 1.5 Make it the string this repo needs

Two edits:

1. Replace `<db_password>` with the password from 1.2 — angle brackets and all.
2. **Insert the database name** between the host and the `?`. `apps/api/src/config/db.ts`
   connects with exactly this URI and no separate `dbName` option, so without a
   database name Mongoose writes to a database called `test`. Use `wroom`.

Final shape:

```
mongodb+srv://wroom_api:REALPASSWORD@wroom-dev.ab12cde.mongodb.net/wroom?retryWrites=true&w=majority&appName=wroom-dev
```

Paste it into `apps/api/.env`:

```
MONGODB_URI=mongodb+srv://wroom_api:REALPASSWORD@wroom-dev.ab12cde.mongodb.net/wroom?retryWrites=true&w=majority&appName=wroom-dev
```

No quotes, no spaces around the `=`.

## 2. Azure Blob Storage → `AZURE_STORAGE_CONNECTION_STRING` + `AZURE_STORAGE_CONTAINER`

You need an Azure subscription. A free trial or pay-as-you-go both work; blob
storage for this project costs pennies.

### 2.1 Create a storage account

1. Go to https://portal.azure.com and sign in.
2. Search bar at the top → **Storage accounts** → **+ Create**.
3. Fill in the Basics tab:
   - **Subscription**: your subscription.
   - **Resource group**: **Create new** → `wroom-dev`.
   - **Storage account name**: globally unique, 3–24 chars, lowercase letters and
     digits only — e.g. `wroommediadev`. If it is taken, add digits.
   - **Region**: the region you plan to host the API in, e.g. `UK South`.
   - **Primary service**: Azure Blob Storage or Azure Data Lake Storage Gen2.
   - **Performance**: Standard.
   - **Redundancy**: **LRS** (cheapest, fine for dev).
4. **Advanced** tab: leave the defaults. In particular leave **Allow enabling
   anonymous access on individual containers** *unchecked* — uploads go through
   time-limited SAS URLs, so nothing needs to be publicly readable.
5. **Review + create** → **Create**. Deployment takes about a minute.
6. **Go to resource** when it finishes.

### 2.2 Create the container

1. In the storage account, left sidebar → **Data storage** → **Containers**.
2. **+ Container**.
3. Name: `media`. Lowercase, no spaces.
4. **Anonymous access level**: **Private (no anonymous access)**.
5. **Create**.

That name is the value of `AZURE_STORAGE_CONTAINER`.

### 2.3 Copy the connection string

1. Left sidebar → **Security + networking** → **Access keys**.
2. You will see **key1** and **key2**. Under key1, find **Connection string**,
   click **Show**, and copy it.

It looks like:

```
DefaultEndpointsProtocol=https;AccountName=wroommediadev;AccountKey=Zm9vYmFy....==;EndpointSuffix=core.windows.net
```

> **It must be an account-key connection string, like the one above.** The API
> signs upload URLs itself (`apps/api/src/services/uploadService.ts`), which
> requires the account key. A SAS-based connection string — one containing
> `SharedAccessSignature=` instead of `AccountKey=` — will connect but every
> upload fails with "File storage is configured without a key that can sign
> upload URLs."

Paste both values into `apps/api/.env`:

```
AZURE_STORAGE_CONNECTION_STRING=DefaultEndpointsProtocol=https;AccountName=wroommediadev;AccountKey=Zm9vYmFy....==;EndpointSuffix=core.windows.net
AZURE_STORAGE_CONTAINER=media
```

The string contains `;` and `=` characters — that is fine. Do not quote it, do
not wrap it across lines.

### 2.4 Allow the browser to upload (CORS)

The browser PUTs files straight to Azure, so the storage account has to allow it.
Storage account sidebar → **Settings** → **Resource sharing (CORS)** → **Blob
service** tab, add one rule:

| Field | Value |
|---|---|
| Allowed origins | `http://localhost:5173` |
| Allowed methods | `PUT`, `GET`, `OPTIONS` |
| Allowed headers | `*` |
| Exposed headers | `*` |
| Max age | `3600` |

**Save.** Add the deployed portal origin here too when you deploy.

## 3. Auth0 → `AUTH0_DOMAIN`, `AUTH0_AUDIENCE`, `VITE_AUTH0_CLIENT_ID`

Auth0 needs **two** things registered: an **API** (what the backend validates
tokens against) and an **Application** (what the portal logs in through). They
are separate objects, and the API is the one people miss.

### 3.1 Create the tenant

1. Go to https://auth0.com/signup and sign up.
2. Pick a tenant name — this becomes your domain, e.g. `wroom-dev` →
   `wroom-dev.eu.auth0.com`. It cannot be changed later.
3. Region: EU. Account type: whatever fits; it does not affect the values.

### 3.2 Register the API → gives you `AUTH0_AUDIENCE`

1. Left sidebar → **Applications** → **APIs** → **+ Create API**.
2. **Name**: `Wroom API`.
3. **Identifier**: `https://api.wroom.local`.
   - This is a unique string, not a URL that gets fetched. It never has to
     resolve. Once set it cannot be changed.
   - Whatever you type here is the **audience**, verbatim, in both `.env` files.
     Watch the trailing slash — `https://api.wroom.local` and
     `https://api.wroom.local/` are different audiences, and a mismatch produces
     a 401 on every request.
4. **JSON Web Token Profile**: Auth0. **Signing Algorithm**: RS256.
5. **Create**.

### 3.3 Register the portal application → gives you `VITE_AUTH0_CLIENT_ID`

1. Sidebar → **Applications** → **Applications** → **+ Create Application**.
2. **Name**: `Wroom Portal`.
3. Type: **Single Page Web Applications**. Not Regular Web App — the portal is a
   Vite SPA with no server session.
4. **Create**. If it offers a quickstart, skip it and open the **Settings** tab.
5. From **Basic Information**, copy:
   - **Domain** — e.g. `wroom-dev.eu.auth0.com`
   - **Client ID** — a 32-character string
   - Ignore **Client Secret** entirely. A SPA cannot keep one, and nothing in
     this repo reads it.
6. Scroll to **Application URIs**. The portal redirects to
   `window.location.origin`, so the dev value is `http://localhost:5173` — no
   trailing slash, no path:

   | Field | Value |
   |---|---|
   | Allowed Callback URLs | `http://localhost:5173` |
   | Allowed Logout URLs | `http://localhost:5173` |
   | Allowed Web Origins | `http://localhost:5173` |

7. Scroll to the bottom → **Save Changes**. Skipping this is the usual cause of
   "Callback URL mismatch" on the first login attempt.

Add the deployed portal URL to all three fields, comma-separated, when you
deploy.

### 3.4 Authorize the application for the API

Registering both objects is not enough — the application has to be granted
access to the API, and it is not linked automatically. Miss this and login fails
with `Client "..." is not authorized to access resource server "..."`.

1. Go to **Applications → APIs → Wroom API → Application Access**.
2. Find **Wroom Portal** in the application list and click it. A panel opens on
   the right with two tabs.
3. Choose **User-Delegated Access** — *not* Client Access. User-delegated is
   Authorization Code + PKCE, which is how a person signs into the portal.
   Client Access is `client_credentials`, for machine-to-machine callers, and
   granting it does nothing for the login flow.
4. Click **Grant Access**.
5. The permission list will be empty until the API has scopes defined. That is
   fine — the grant is what matters, and it can hold zero permissions. Tick
   **Always grant all permissions** so new scopes are picked up automatically.
6. **Save**. The row's User-delegated Access column should now show a green check.

> Older Auth0 tenants show this as an **APIs** tab on the application, or a
> **Machine to Machine Applications** tab on the API, with a simple Authorized
> toggle. Same underlying grant, different UI.

The **Current access policy** shown above the list explains why this step exists
at all: when it reads **Per-app authorization**, every application must be
granted explicitly before it can request tokens for this API.

### 3.5 What goes where

`AUTH0_DOMAIN` is the **bare host** — no `https://`, no trailing slash. The API
builds the issuer URL itself (`apps/api/src/middleware/auth.ts` does
`https://${domain}/`), so a pasted `https://` prefix produces a malformed issuer
and every token fails.

In `apps/api/.env`:

```
AUTH0_DOMAIN=wroom-dev.eu.auth0.com
AUTH0_AUDIENCE=https://api.wroom.local
```

In `apps/portal/.env`:

```
VITE_AUTH0_DOMAIN=wroom-dev.eu.auth0.com
VITE_AUTH0_CLIENT_ID=aBcD1234eFgH5678iJkL9012mNoP3456
VITE_AUTH0_AUDIENCE=https://api.wroom.local
```

The two audience values must match character for character, and both domains
must match. If the audience is missing or wrong on the portal side, Auth0 issues
an opaque token instead of a JWT, and the API rejects it with a 401 that looks
nothing like a config error.

> **First sign-in becomes the owner.** `loadCurrentUser` makes the first person
> to log in against an empty `users` collection the owner; everyone after starts
> as a viewer. So sign in with your own account first.

## 4. The finished files

`apps/api/.env`:

```
NODE_ENV=development
PORT=4000

MONGODB_URI=mongodb+srv://wroom_api:REALPASSWORD@wroom-dev.ab12cde.mongodb.net/wroom?retryWrites=true&w=majority&appName=wroom-dev

AUTH0_DOMAIN=wroom-dev.eu.auth0.com
AUTH0_AUDIENCE=https://api.wroom.local

AZURE_STORAGE_CONNECTION_STRING=DefaultEndpointsProtocol=https;AccountName=wroommediadev;AccountKey=...==;EndpointSuffix=core.windows.net
AZURE_STORAGE_CONTAINER=media

CORS_ORIGINS=http://localhost:5173,http://localhost:5174

GITHUB_APP_TOKEN=
STRIPE_SECRET_KEY=
ANTHROPIC_API_KEY=
```

Leave the last three blank — nothing reads them yet.

`apps/portal/.env`:

```
VITE_API_BASE_URL=http://localhost:4000
VITE_AUTH0_DOMAIN=wroom-dev.eu.auth0.com
VITE_AUTH0_CLIENT_ID=aBcD1234eFgH5678iJkL9012mNoP3456
VITE_AUTH0_AUDIENCE=https://api.wroom.local
```

`apps/portfolio/.env`: already complete, nothing to add.

## 5. Verify

```bash
npm install
```

```bash
npm run dev:api
```

The API reads its environment once at boot, so a missing variable fails
immediately with the name of the variable rather than later, on whichever
request happens to need it.

Check Mongo is actually connected:

```bash
curl http://localhost:4000/health
```

Expect `{"data":{"status":"ok","database":"connected"}}`. If `database` says
`connecting` or `disconnected`, the URI or the IP allowlist is wrong.

Then the portal:

```bash
npm run dev:portal
```

Open http://localhost:5173 and sign in. If the shell shows a setup message
instead of a login button, `VITE_AUTH0_DOMAIN` or `VITE_AUTH0_CLIENT_ID` is
empty — **Vite only reads `.env` at startup**, so restart the dev server after
any edit.

## 6. When it does not work

| Symptom | Cause |
|---|---|
| Boot error naming a variable | That variable is blank in `apps/api/.env`. |
| `/health` shows `database: "connecting"` forever | IP not in Atlas Network Access, or the password is wrong or has unencoded symbols. |
| `MongoServerError: bad auth` | Wrong password, or `<db_password>` placeholder still in the string. |
| Data lands in a `test` database | Missing `/wroom` before the `?` in the URI. |
| `Callback URL mismatch` at login | `http://localhost:5173` not saved in Allowed Callback URLs. |
| `Client "..." is not authorized to access resource server "..."` | The application is not authorized for the API. Fix it in the dashboard (§3.4), not in `.env` — this error means the audience string is *correct*, since Auth0 resolved the resource server by name. |
| `Service not found: <audience>` | The audience string does not match any API Identifier. This one *is* an `.env` problem — check for a stray trailing slash. |
| Login succeeds, every API call 401s | Audience mismatch between the two `.env` files, or `https://` left on `AUTH0_DOMAIN`. |
| Portal shows the setup message | Portal `.env` empty, or dev server not restarted after editing it. |
| Upload fails, "not configured on this environment" | `AZURE_STORAGE_CONNECTION_STRING` or `AZURE_STORAGE_CONTAINER` blank. |
| Upload fails, "no key that can sign upload URLs" | SAS connection string instead of an account-key one. |
| Upload URL returned but the browser PUT fails | Blob service CORS rule missing on the storage account. |

## 7. Keeping the values safe

- `.env` is gitignored — check `git status` before committing; it should never
  appear.
- Never paste a real value into `.env.example`, a comment, a fixture, or seed
  data. That file holds names only.
- Rotate a leaked value at the source: Atlas → Database Access → Edit password;
  Azure → Access keys → Rotate key1. The Auth0 Client ID is public by design and
  does not need rotating.
- For deployment the same names go into Azure App Service **Configuration →
  Application settings** and Render/Vercel **Environment Variables**, not into
  files. Remember to add the production origins to `CORS_ORIGINS`, the Auth0
  application URIs, and the storage CORS rule.
