# CLAUDE.md — Wroom

This file is the **constitution** for this repo. It defines the stack, the rules, and how work is done here.

It does **not** contain the feature list. That lives in `FEATURES.yaml`, generated by Wroom itself. Never plan work from this file — plan it from the **work order** you were given. A work order is either a ticket or a tagged instruction (§2.1).

---

## 1. What this is

**Wroom** is a development war room. Two frontends, one backend, one database.

| App | Who uses it | Auth |
|---|---|---|
| **Portal** (`apps/portal`) | Jaya and the Teczo team | Required |
| **Portfolio** (`apps/portfolio`) | Public — clients, employers | None |
| **API** (`apps/api`) | Both frontends | Split by route namespace |

The portal manages projects, infrastructure, costs, features, time and media. The portfolio is a public showcase built from a **published snapshot** of that data — it never reads the operational collections.

The data model is specified in `docs/DATA_MODEL.md`. **That document is authoritative.** If a work order seems to require a schema change, stop and report — do not invent collections or fields.

---

## 2. Golden rules

These override anything else in this file.

1. **Build only what the work order asks for** — the ticket's acceptance criteria, or the sentences of a `developnow` prompt (§2.1). No adjacent improvements, no "while I was in there". If you spot something worth doing, write it in the report — do not do it.
2. **Never add a dependency without asking.** Report what you want and why, then stop.
3. **Never edit `FEATURES.yaml`** unless the prompt explicitly says *offline mode* (see §9).
4. **Never invent schema.** Fields and collections come from `docs/DATA_MODEL.md`.
5. **Never write a secret into the repo**, including `.env`, test fixtures, comments, or seed data. `.env.example` holds names only.
6. **Stop and report rather than retry.** If you're blocked, or a fix hasn't worked after two attempts, stop. Do not try a third approach, do not work around it, do not stub it out silently.
7. **No mock data in committed code.** If an endpoint isn't built yet, the frontend shows an empty state, not a fake array.

### 2.1 Two ways to start work

Every session runs in one of two modes. Pick the mode before you touch anything.

| Mode | How it starts | What it's for |
|---|---|---|
| **Ticket mode** — the default | The prompt carries a ref (`WRM-014`) or a full ticket | New features, and anything touching schema, auth, publishing, `/public`, money, or more than one app |
| **`developnow`** | The prompt contains the literal word `developnow` | Bug fixes, copy and layout changes, small self-contained additions to something that already exists |

If the prompt has neither a ref nor a tag, ask which one it is. One question, then wait.

**In `developnow` mode:**

- **The prompt is the ticket.** Its sentences are the scope and the exit criteria. Nothing outside them gets built.
- Do not look for a ticket, do not ask for one, do not write one.
- Do not read `FEATURES.yaml` for direction, do not create a ref for the work, do not touch the file at all.
- Branch `now/short-description`. Commit and push. A PR is optional — say in your report that the branch is up.
- Report in the short form below, not the §11 block.
- Still add one sentence to `CHANGELOG.md` under today's heading.

```
CHANGED  — what is different now, in one sentence
CHECK    — the screen or URL to look at, so it can be confirmed on a phone
NOTICED  — anything worth a ticket later — do not fix it now
```

**`developnow` relaxes the ceremony, not the constitution.** §3 (stack), §6 (API conventions), §7 (frontend conventions), §8 (security), §10 (definition of done) and §11 (stop-and-report) apply unchanged. `npm run lint` and `npm run build` still have to pass in every app touched, and it still has to work at 390px.

**Escalate back to a ticket** — stop, say so, build nothing — the moment the work turns out to need any of:

- a schema change, a new collection, or a new field
- a new dependency
- a new route in either namespace, or any edit to the `/public` allowlist
- a change to auth, the three publish gates, upload handling, or the enquiry endpoint
- a change to `projects.rollup`, or to any money or FX calculation
- a new file under `/models`, `/routes` or `/services`
- work in both frontends at once, or more than roughly five files

The words are: *"This is bigger than a `developnow` — it wants a ticket. Here is what the ticket would say."* Then stop. A `developnow` that quietly grew into a feature is the exact failure this repo exists to prevent.

**`hotfix`** is `developnow` with production broken. Same rules, plus: the smallest diff that stops the bleeding, branch `hotfix/short-description`, and the report must say whether the cause is fixed or only the symptom.

## 3. Stack — locked

Do not substitute any of these.

**Frontend (both apps)** — React 18, Vite, Tailwind CSS, React Router, TanStack Query for server state, plain React state locally.

**Backend** — Node 24, Express 5, Mongoose. REST, not GraphQL.

**Database** — MongoDB Atlas.

**Auth** — Auth0 (portal only; portfolio is unauthenticated).

**Storage** — Azure Blob Storage for all uploads.

**Hosting** — Portal and portfolio on Render or Vercel. API on Azure App Service.

### Explicitly not used

Next.js · Postgres or any SQL database · Firebase · Prisma · Redux · GraphQL · any component library that ships its own design system (build components on Tailwind).

If a work order appears to need one of these, stop and report.

## 4. Repo structure

```
/apps
  /api          Express 5 backend
  /portal       React — authenticated management app
  /portfolio    React — public showcase
/packages
  /shared       Types, constants, validation schemas used by more than one app
/docs
  DATA_MODEL.md
CLAUDE.md
FEATURES.yaml   Generated by Wroom — do not hand-edit
CHANGELOG.md
```

Inside `apps/api`:

```
/src
  /config       env loading, db connection
  /models       Mongoose schemas — one file per collection
  /routes       Express routers — mirrors the resource name
  /controllers  request/response handling only
  /services     business logic — all of it
  /middleware   auth, validation, error handling
  /jobs         scheduled tasks (exports, cost sync)
  /utils
```

Inside each frontend:

```
/src
  /pages        one folder per route
  /components   shared UI
  /features     feature-scoped components + hooks
  /lib          api client, helpers
  /hooks
```

**Controllers stay thin.** Business logic lives in services. A controller that does anything more than validate, call a service, and shape a response is wrong.

## 6. API conventions

**Two namespaces, and the split is a security boundary.**

- `/api/*` — Auth0 JWT required on every route. Full access to all collections.
- `/public/*` — no auth. **Every route must appear in this allowlist:**

```
GET   /public/projects         → publishedProjects            (read)
GET   /public/projects/:slug   → publishedProjects            (read)
GET   /public/content/:key     → siteContent.published only   (read)
POST  /public/enquiries        → enquiries                    (write, reads nothing)
```

Adding a route to `/public` is an edit to this file, not a decision made inside a session.

A `/public` handler may never query `projects`, `costs`, `revenue`, `accounts`, `credentials`, `services`, `timeEntries` or `users`. It may never return the `draft` sub-document of `siteContent`. If a work order seems to ask for any of this, stop and report — a `developnow` tag does not buy an exception.

**Shape.** Resource-based, plural: `/api/projects`, `/api/projects/:id/features`. Standard verbs. Validate every request body with the shared schema in `packages/shared`.

**Responses.**

```js
// success
{ data: {...} }
{ data: [...], meta: { total, page, limit } }

// error
{ error: { code: "VALIDATION_FAILED", message: "Human readable", details: {...} } }
```

Status codes: 200, 201, 400, 401, 403, 404, 409, 422, 500. No 200-with-error-body.

**Errors.** Throw typed errors from services; a single error middleware maps them to responses. Never `res.status(500).send(err.message)` — that leaks internals.

**Rollups.** `projects.rollup` is denormalised. Recompute it in the service layer whenever a feature, cost, revenue entry or time entry changes for that project. Do not use change streams.

## 7. Frontend conventions

- Server state through TanStack Query. No fetching in `useEffect`.
- One API client in `src/lib/api.ts`. Components never call `fetch` directly.
- Every list view handles four states explicitly: loading, empty, error, populated. An empty state must say what to do next, not just "No data".
- Forms in the portal are **schema-driven** where the data model says so — project type forms render from `projectTypes.fieldDefs`, they are not hardcoded per type.
- Tailwind utility classes inline. No CSS modules, no styled-components. Shared visual patterns become components, not `@apply` blocks.
- Mobile-first. Every portal view must be usable at 390px width — the whole point of this app is checking work on a phone.

## 8. Security rules

**The three publish gates.** An asset appears in the portfolio only if all three are true:

1. `asset.visibility === "public"`
2. `project.portfolio.visibility === "public"`
3. `product.ndaRestricted === false`

Implement this as one shared function. Never inline the check.

**Defaults are private.** New projects and new assets are created private. There is no "publish on save" path — publishing is an explicit action that writes `publishedProjects`.

**Credentials collection stores locations, never values.** `storedIn` is a human-readable pointer like `"Azure Key Vault"`. If a work order asks you to store a key value, stop and report.

**Uploads.** Validate mime type and size server-side. Generate SAS URLs with expiry; never expose the storage connection string to a client.

**The one public write.** `POST /public/enquiries` is the single unauthenticated write in the system. It must:

- validate the whole body with a Zod schema from `packages/shared` — reject any non-string where a string is expected, which is what closes NoSQL injection
- set `status`, `source`, `ownerUserId`, `convertedToProductId`, `meta` and timestamps server-side, stripping them from the body if present
- rate limit per IP, cap total submissions per day, and cap body size
- reject a filled honeypot field or a submission completed implausibly fast
- read no collection at all

Enquiry text renders as plain text in the portal, never as HTML.

**Published content only.** `GET /public/content/:key` returns the `published` sub-document of a `siteContent` record. If `published` is null the route returns 404. The `draft` sub-document must never leave an `/api/*` route.

## 9. Feature workflow

`FEATURES.yaml` is **generated by Wroom**. The database is the source of truth; this file is an export.

**Normal mode — the default.**
- Read `FEATURES.yaml` at the start of a ticket-mode session to understand what exists. In `developnow` mode, don't read it at all.
- **Do not edit it.** Not the status, not the ordering, not a new entry.
- Report completion in `CHANGELOG.md` and in your closing message.

**Offline mode — only when the prompt says "offline mode".**
- You may update `status` and `completedAt` on entries you completed.
- You must set `offlineEdits: true` in the file header.
- Change nothing else in the file.

**Branches.** One branch per feature ref: `feat/WRM-014-short-description`. PR title starts with the ref. Squash merge to `main`.

Untickled work has no ref, so it gets its own prefixes: `now/short-description` and `hotfix/short-description` (§2.1). The prefix is how the history shows, at a glance, which changes went through a ticket and which didn't. Never add untickled work to `FEATURES.yaml` — not in normal mode, not in offline mode.

## 10. Definition of done

A feature is done when all of these hold:

- It does exactly what the work order states — the ticket's acceptance criteria, or the sentences of the `developnow` prompt — no more.
- It works against a real MongoDB connection, not mocks.
- Loading, empty and error states are handled in any UI touched.
- It renders correctly at 390px and at desktop width.
- No console errors or warnings introduced.
- No secret, key, or real account email committed.
- `npm run lint` and `npm run build` pass in every app you touched.
- `CHANGELOG.md` has a new entry (see §11).

If you cannot satisfy every line, the feature is not done. Say so.

## 11. Stop-and-report protocol

**Stop immediately and report** when any of these happen:

- The work order needs a schema change not in `docs/DATA_MODEL.md`
- The work order needs a new dependency
- The work order needs a stack element from the "not used" list
- A credential or external service is missing or rejecting you
- The work order contradicts a rule in this file
- Two attempts at a fix have failed
- The work order is ambiguous enough that you'd be guessing at intent
- A `developnow` hits any escalation trigger in §2.1

Do not push past any of these. A stopped session with a clear question is a good outcome; a session that guessed and built the wrong thing is not.

**Every session ends with a report, in plain language.** No architecture jargon, no file-by-file narration. Ticket mode uses the block below; `developnow` uses the three-line form in §2.1.

```
DONE
- <what a user can now do that they couldn't before>

NOT DONE
- <anything from the ticket you didn't finish, and why>

BLOCKED
- <what stopped you, and what you need from Jaya to continue>

NOTICED
- <anything worth fixing later — do not fix it now>
```

Append the same DONE lines to `CHANGELOG.md` under a dated heading.
